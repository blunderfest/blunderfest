# Code Review 2 — 2026-08-11

Second full review, focused on *idiomatic use*: React/Redux on the frontend
(hooks discipline, selector hygiene, effects) and Elixir/Phoenix/OTP on the
backend (GenServer boundaries, channel design). Complements [REVIEW.md](REVIEW.md)
(2026-08-06); findings from it are only restated when their state changed.

The first review's verdict stands: the architecture bets (op log, no-DB,
per-room processes + Horde) are executed coherently and the test culture is
real. The frontend is *mostly* exemplary React — effects are few and each is
a genuine external-system sync (channel, engine worker, window listeners,
debounce); the two `useExhaustiveDependencies` suppressions are legitimate
(retry counter, trigger-on-id). The findings below are refinements, not
rethinks.

## Findings, by severity

### 1. Clients replay `set_game` trees without validation — a crafted op crashes the room for everyone ⚠️ TOP FINDING ✅ FIXED (2026-08-11)

`Ops.validate/1` now walks the whole tree: every node must carry an integer
`id`/`ply` and a `children` list (nullable string fields and `nags`
type-checked), and the tree is capped at 2,000 nodes / 1,500 deep, so a
256 KB op can no longer crash or stack-overflow clients on replay.

~~Original finding:~~

`Ops.validate/1` checks only that a `set_game` payload has `tree.root`
(`ops.ex:47-52`). The client replays it blindly: `applyOp`/`replayOps`
(`store/room.ts`) assign the tree, then `buildNodeMap`
(`features/analysis/nodeMap.ts:11`) does `node.children.forEach(...)` and
`findNode`/`maxNodeId` recurse unbounded. A malicious room editor can push a
256 KB op with `children` missing (TypeError during render — no error
boundary exists, so the whole app unmounts) or nested ~18k deep (stack
overflow in the recursive reducers). Because the op is in the room's log,
*every* join replays it — the room is bricked until its process dies.
Review 1 #2 closed the malformed-op door for every other type; `set_game`
carries a whole recursive structure and got a shallow check.

**Fix:** validate the tree server-side at ingest (node count, depth, and
per-node shape caps — a few lines in `Ops`), and/or make client replay
defensive (depth-cap the recursion). Server-side is the real fix: the log
is the shared source of truth.

### 2. Out-of-order ops are silently dropped — a rare but permanent desync ✅ FIXED (2026-08-11)

The client now applies echoes strictly in `seq` order: an exact successor is
applied, a stale/duplicate seq is ignored, and a gap triggers a resync by
rejoining the channel (replay replaces the store wholesale). Covered by
`useRoomChannel` tests.

~~Original finding:~~

`applyOp` (`store/room.ts`) applies an op only if `op.seq > lastSeq`.
Phoenix PubSub preserves order *per publisher process*, but two members
editing simultaneously publish from different channel processes, so the
echoes can interleave: seq 6 can reach a client before seq 5, and seq 5 is
then dropped forever — that client shows a different board until it
rejoins. No gap detection, no recovery.

**Fix:** on `op.seq > lastSeq + 1` (a gap), resync — re-join the channel or
refetch the log — instead of applying. Buffering works too; resync matches
the "replay is the one path" philosophy (ADR-0005) and is a few lines in
`useRoomChannel`/`applyOp`.

### 3. Permission check and append are separate room calls — TOCTOU race + cross-region latency ✅ FIXED (2026-08-11)

`Rooms.submit_op/3` now permission-checks and appends atomically inside the
room process (read-only → `:read_only`, edit without rights → `:forbidden`,
cap → `:op_limit`), and `Rooms.join_snapshot/3` returns `{ops, roles,
read_only}` with the claim in one call. Joins do one room call instead of
four, ops one instead of three — one cross-node RTT each.

~~Original finding:~~

`RoomChannel.handle_in("op")` does three GenServer calls per op:
`read_only?`, `can_edit?`, `append`. Between `can_edit?` and `append`, an
owner's `set_role` demote can slip in and the demoted member's edit still
lands (serialized per room, but the check and the append are different
messages). Also, per ADR-0013 each cross-node call is ~85 ms, so a
far-region op costs 2–3 RTTs. Joins do four calls (`claim`, `ops`,
`roles`, `read_only?`) — ~350 ms cross-region.

**Fix:** one atomic `Rooms.submit_op(slug, profile_id, op)` that checks
read-only/permission and appends inside the room process; one
`Rooms.join_snapshot(slug, profile_id)` returning `{ops, roles,
read_only}` after claiming. Fewer races, one RTT each.

### 4. `Analysis.tsx` doubled since review 1 flagged it (440 → 949 lines)

Review 1's "god-component" note said the cursor/engine logic would extract
cleanly before milestone 6. Instead it absorbed edit mode, annotations, the
keyboard map, and the pending mechanism. It now holds ~10 pieces of state
and 5 responsibilities. The extraction targets are unchanged and still
clean: `useCursor` (cursor + follow-the-tail + presenter sync), the
edit-mode cluster (`editing`/`editPos`/`editBrush`/... + handlers), and
`useBoardKeyboard`. Not urgent — tests are good — but it keeps growing.

### 5. The `pending` map never shrinks, and a rejected op leaves a phantom node

`Analysis.tsx:156` — `setPending` only ever adds. Entries are shadowed by
the echoed tree node but never deleted (bounded by ops-per-mount, so the
memory is trivial). The sharper edge: if the server *rejects* the op
(op_limit, a mid-edit demote), no echo arrives and the author keeps seeing
a move that doesn't exist for anyone else — silent divergence until
refresh. A rejected op should roll back the pending entry (push op with
`receive('error', ...)`) or at least be droppable.

## Smaller React/Redux items

- **`ActivityFeed` mutates a ref during render** (`ActivityFeed.tsx:57-60,81-84`:
  `seen.add(op.seq)` inside the row map). Under StrictMode's double render
  the first pass marks everything seen, so the committed (second) output
  never gets the `animate-arrive` class — the flash is dev-only-dead, and
  the pattern is the one React explicitly calls out (render must be pure).
  The codebase already knows the idiomatic fix — the render-adjust pattern
  used in `Analysis.tsx:209-213` — apply the same here.
- **`ActivityFeed` labels decay on leave:** `presence[op.author]?.name ??
  op.author` rewrites history to raw profile ids when the author leaves the
  room. Snapshot the display name per op arrival (or keep a `nameById` map
  in the store) if the feed should read as history.
- **Two hot selectors scan the whole op log on every dispatch:**
  `selectPresenterGameId` and `selectPresenterCursor` (`store/room.ts`)
  are plain functions; cursor ops make every dispatch, so a presenting
  session re-scans thousands of ops per navigation. Wrap in
  `createSelector` like `selectSortedMembers`/`selectActivityOps` already
  are. (The `?? {}` annotations fallback fixed this session was the same
  class of issue.)
- **Escape clears annotations without checking `canEdit`**
  (`Analysis.tsx:545-551`): viewers send a doomed `set_annotations` op on
  every Esc. The `c` key two branches down gates correctly; this one
  doesn't. Harmless (server rejects) but sloppy and inconsistent.
- **Engine retry can't recover from the failures it exists for:** once the
  handshake rejects or the worker dies, `engine.ts` caches the rejected
  `initialized` promise and `getSharedEngine()` keeps the dead worker, so
  the Retry button (`EngineReadout`) only ever re-runs the same failure.
  Reset `initialized` on failure and recreate the worker on fatal error.
- **`engine.ts` leaks a listener per superseded search** unless the caller
  aborts first — the "callers must abort" contract is enforced only by
  convention (useEngine honors it). Post `stop` and drop stale listeners
  when a new search starts; defense in depth.
- **`useProfile` never passes its AbortSignal to fetch** — aborting only
  skips the `setState`. Under StrictMode's dev double-mount, a first-visit
  bootstrap fires `createProfile` twice (orphan profile, dev-only). Pass
  `signal` into `fetchProfile`/`createProfile`.
- **Board's window listeners and long-press timer have no unmount
  cleanup** (`Board.tsx` `startDraw`, `handlePointerDown`): unmounting
  mid-gesture (switching games mid-drag) leaves them attached until the
  next pointer event, and a finishing draw can fire for the previous
  game's node id. One unmount effect clearing refs/listeners closes it.
- **`generateRoomCode` uses `Math.random()`** (`lib/roomCode.ts`): codes
  are capability links; `crypto.getRandomValues` is a drop-in and the
  codebase already uses `crypto.randomUUID()` elsewhere.

## Smaller backend/Elixir items

- **Two moduledocs describe features the code doesn't have:**
  `user_socket.ex` claims an optional Phoenix.Token device-token claim, but
  `connect/3` ignores params entirely; `node_info.ex` says room processes
  carry the region as their Horde registry value, but `Room` registers
  `{registry, slug}` (no value). Delete the docs or implement the feature —
  stale docs are worse than none. Related drift: `architecture.md` puts
  `Board.tsx` under `features/analysis/`; it lives in `components/`.
- **`Plug.Parsers` keeps the 8 MB default** while the largest legitimate
  body is a 256 KB PGN; oversized requests 413 via the generic `ErrorJSON`,
  not a structured code (ADR-0003). Set `length:` and map the error.
- **`String.to_atom` in `pgn.ex:502`** is safe only by regex construction —
  but the 12 atoms (`:wk`, `:bq`, ...) already exist as `Echecs.Board`
  function names, so `String.to_existing_atom` is a drop-in that makes it
  provably safe.
- **`/api/games/moves` is still routed, still unused** by the client since
  legal moves went local (review 1 #6). Keep it deliberately (public API)
  or delete it; decide either way.
- **`Rooms.reset/1` polls with `Process.sleep(10)`** — acceptable for a
  test-only seam, noted only because the test guidelines forbid it in
  tests; it lives in production code, test-driven.

not a rethink), the no-DB stance, per-room processes behind the `Rooms`
facade, op validation at the channel edge, the `FakeChannel`/injectable
engine test seams, `Board`'s effect-free gesture handling, and the
hand-rolled PGN parser with its golden fixtures.
